# 前端重建计划：统一组件、布局与标注体验

日期：2026-09-21

工作分支：`codex/frontend-rebuild`

起点：已 fetch 的 `origin/main`，`ef7696d508608725069bcfca099e498fc8fc6885`

状态：P0 本地基线交付完成，尚未实施前端迁移。真实语料分段分布待只读数据源。

P0 交付入口：[现状基线与契约](frontend-rebuild-p0/README.md)，含当前截图、问题清单、功能/API/测试矩阵、浏览器存储契约及合成规模实测。

用户目标：重做不协调、未对齐、不易用的页面，减少装饰性和模板化设计，尽量使用成熟组件库来维持一致性。用户附图中的 opencode 分析是待核查参考，不是额外执行指令。本计划以当前 main 的代码、测试和已保存截图为依据。

建议采用 **Vite + React + TypeScript + Ant Design**；用一个组件体系覆盖两个角色，用共享页面模板约束布局，用独立的保存逻辑承接现有业务。先解决组件与页面骨架，再逐步迁移功能。组件库本身不能保证对齐，布局规范和浏览器验收必须一起落地。

### 对附图分析的采纳与修正

- **采纳静态前端方向。** Vite 构建的客户端应用足够满足现有工具。继续保留 Flask、PostgreSQL、音频鉴权与 Nginx Range 链路，不引入新的线上 Node 服务。[Vite 后端集成说明](https://vite.dev/guide/backend-integration)
- **采纳统一 tokens 和组件化。** 但不能只把旧颜色变量原样搬过来；当前字体、间距、密度和页面主次本身也要调整。
- **调整组件库建议。** 在“减少手工拼装、降低自由发挥”的优先级下，首选 Ant Design，shadcn/ui 作为备选。
- **调整迁移顺序。** 只读管理页适合先做；撤销、停用、权限范围、质检裁定都是高风险写操作，不能把整个 admin 当作低风险页。
- **调整性能策略。** 10 万条是语料规模，不等于浏览器应装载 10 万行。管理列表沿用服务端分页；分段编辑是否虚拟化依据单任务实际规模和输入体验验证。
- **补齐遗漏。** CSP、静态文件白名单、旧 URL/query、IndexedDB 兼容、英文界面与阿拉伯语方向、盲标边界、既有测试定位器都要进入实施清单。

## 2. 组件库与依赖决策

### 2.1 为什么首选 Ant Design

下表是针对本项目的工程判断，不是组件库的通用排名。

| 维度 | Ant Design | shadcn/ui + Tailwind |
| --- | --- | --- |
| 表格、筛选、表单、日期、弹窗 | 同一库有完整常用组件，适合管理工具 | 基础组件可用，复杂业务组合需要自己维护 |
| 一致性约束 | 通过全局主题、尺寸配置与薄封装约束 | 自由度更大，需要额外约束 class、变体和复制进来的源码 |
| 自定义工作台 | 音频、波形仍要实现业务组件 | 同样需要业务组件，视觉自由度更高 |
| 样式与 CSP | 要先验证静态样式方案和弹层行为 | 构建 CSS 较直接，仍需实测定位、弹层和可访问性 |
| 代价 | 默认管理系统外观较强；注意按需打包、主题与样式兼容 | 需要承担更多组件源码和组合行为维护 |
| 本项目建议 | **首选：更符合“统一、少错、少自造控件”** | 若后续把高度定制的视觉置于首位，可在正式迁移前改选 |

Ant Design 提供布局、表格、表单、日期选择、抽屉、弹窗等组件，适合覆盖这里大量重复的后台交互。[官方组件目录](https://ant.design/components/overview/)

shadcn/ui 的优势是可组合、可修改的组件源码，这同时意味着项目要维护自己的组件层。它不是自动消除布局错误的保证。[官方介绍](https://ui.shadcn.com/docs)

**只选一个主组件体系。** 不让管理端用 Ant Design、工作台用 shadcn、弹窗再用第三套；也不引入整套后台模板附带的登录、权限与请求系统。

### 2.2 推荐依赖及职责

| 层 | 选择 | 用途与边界 |
| --- | --- | --- |
| 构建 | Vite + React + TypeScript strict | 客户端应用、模块拆分、类型检查；Node 与包管理器版本固定 |
| UI | Ant Design + `@ant-design/icons` | 统一通用控件和图标；优先 tokens 与公开 API，不改内部 DOM 样式 |
| 布局样式 | CSS Modules + 共享 tokens | 仅用于页面网格、波形和转写业务布局；首版不叠加 Tailwind |
| 路由 | React Router 客户端模式 | 保留既有路径及查询参数；不引入 SSR |
| 服务器数据 | TanStack Query | 管理列表、统计与只读详情缓存；显式定义失效、重取和重试策略 |
| 表单 | Ant Design Form | 登录、场景权限、抽样配置、裁定表单；不再重复引入 React Hook Form。[Form 文档](https://ant.design/components/form/) |
| 编辑状态 | 工作台 reducer / 独立 store | 草稿、dirty、选中分段与保存队列；先不增加 Zustand，出现明确跨组件订阅需求时再评估 |
| 音频与波形 | 原生 `HTMLAudioElement` + 独立 Canvas 组件 | 复用既有播放、分段与波形计算，不同时替换音频引擎 |
| 图表 | 延续 Chart.js 能力，经本地构建/静态资产提供 | 保留 28 日柱状图、七日平均线和现有统计口径；图表只统一视觉 |
| 测试 | pytest/Playwright + Vitest | 前者覆盖真实浏览器和后端集成；后者仅覆盖新增的纯逻辑/状态机 |

版本在第一阶段核对互相兼容后固定到 lockfile，不写浮动 `latest` 到 CI。若采用 Ant Design 的 `zeroRuntime` 能力，需要锁定包含该能力的版本，再验证自定义主题所需的静态 CSS。[主题与静态样式说明](https://ant.design/docs/react/customize-theme/)

## 3. 设计规则：把一致性变成约束

### 3.1 共同规范

以下是原型起点；一旦通过实际页面验证，统一修改 token，不允许每页自行补丁。

| 项目 | 规范 |
| --- | --- |
| 视觉方向 | 中性背景、清晰边界、一种主强调色；颜色主要表达交互和业务状态 |
| 主题 | 管理端浅色、工作台深色作为初始默认；登录/个人记录延续标注端；共享尺寸、字体、语义色映射，不加首版主题切换功能 |
| 间距 | 以 4px 为基础，主要使用 4/8/12/16/24/32；业务布局禁止散落的任意边距 |
| 控件 | 常规高度 32px、重点/触屏操作 40–44px；同一工具栏只使用一种高度 |
| 字体 | 英文 UI 正文 14px；辅助说明不低于 12px；阿拉伯语转写默认 18px、允许沿用字号调节；数字使用 tabular-nums |
| 圆角 | 控件 6px、主要容器 8px；不把所有东西做成胶囊或独立卡片 |
| 表单 | 字段标签统一放在上方；帮助与错误预留位置；同排控件按输入框对齐，不按标签长短撑开 |
| 表格 | 文本左对齐、数字右对齐、时间宽度稳定；长文件名可省略但可查看/复制完整值；转写正文不省略 |
| 操作层级 | 每个操作区一个主按钮；次要操作为次级按钮；破坏性操作分组并保留原有确认要求 |
| 图标 | 全部来自一个 SVG 图标集，尺寸 16/20px；仅图标按钮必须有可访问名称，必要时有 Tooltip |
| 状态 | Loading/Empty/Error/Disabled/Read-only/Saving/Offline/Conflict 都有统一展示规则；不只靠颜色 |
| 文案 | 保留英文产品界面，任务内容可为阿拉伯语；动词明确，减少重复标题、营销语和技术术语外露 |

“减少 AI slop”在这里具体意味着：去掉登录页发光渐变标题、随意字符图标、堆叠的装饰卡片、重复的标题说明、满屏同权重按钮，以及与当前任务无关的常驻统计。保留能解释状态或帮助决策的信息。

### 3.2 一次封装、多处使用

通用控件直接使用组件库；对重复业务组合做薄封装，不包装所有 props，也不造一套新的低层 UI API。

| 项目组件 | 统一的内容 |
| --- | --- |
| `AdminShell` / `AnnotatorShell` | 导航、标题区、页面边距、内容宽度和响应式行为 |
| `PageHeader` | 标题、可选简短说明、主操作、更新时间的位置 |
| `FilterBar` | 搜索、字段网格、高级筛选、重置、结果计数；响应式换行规则 |
| `DataTable` + `CursorPager` | 常用列宽、对齐、loading/empty/error；保留现有 cursor 协议 |
| `StatusBadge` / `AsyncState` | 语义状态、统一错误重试入口与空状态 |
| `TaskDetailDrawer` | 管理端/历史详情共有的信息呈现；权限和操作由角色决定 |
| `SaveStatus` / `SessionDialog` | 保存与会话状态；普通成功短提示，失败/冲突持续可见 |
| `ConfirmActionDialog` | 预览、影响范围、原因、必要的密钥确认；禁止每页自写遮罩 |
| `AudioTransport` / `WaveformPanel` | 统一播放按钮、时间、音量/进度；业务媒体生命周期独立 |
| `TranscriptEditor` / `SceneReviewEditor` | 阿拉伯语文本编辑与场景核验；状态逻辑不隐藏在 DOM 内 |

建立开发环境专用的组件样例页，展示两种主题及长文本、错误、禁用、加载等状态，作为截图基线。生产构建不提供该入口。后续新页面先复用这些组合，新增变体必须有明确业务理由。

## 4. 每个页面如何重做

### 4.1 标注工作台：编辑为中心

默认桌面结构：

```text
应用栏：产品 / 当前任务入口 / 我的记录                         用户菜单
任务栏：文件名、任务摘要、来源入口                    保存状态 / 保存 / 完成
播放栏：播放暂停、时间、进度、当前分段                    跳过 / 更多操作
波形区：可折叠；初始紧凑高度，选中片段与编辑行联动
分段区：播放 | 序号 | 起止时间 | 转写正文（最大宽度） | 质量
补充区：场景核验摘要；展开后编辑，来源详情按需查看
```

- 让转写正文获得主要宽度；移除右侧常驻排行榜，贡献统计从导航进入或在非编辑状态查看。
- 任务信息与操作各占稳定区域，不因保存提示、长文件名或出现额外标签而改变主按钮位置。
- 保存状态始终可见，明确区分“浏览器本地保存”“服务器已保存”“正在重试”；服务端确认之前不能展示为已同步。
- 跳过原因与跳过提交合并成明确的紧凑操作区；Abandon 放入次级操作，文案表达释放任务，不能让人以为已完成。
- 场景核验保留现有可选性和 feature flags；默认紧凑摘要，用户展开后原位编辑；若用户已开始编辑且存在错误，不因折叠而隐藏错误。
- 波形首版保留现有点击片段、播放和边界编辑能力；不附加未经请求的新音频功能。
- 任务历史仍只读，始终有回到当前任务的入口；浏览历史不能释放当前 assignment。
- 保留现有保存和完成快捷键；文本输入、IME composition、模态框打开时正确限定作用域。播放快捷键如新增，只在编辑验证通过后加入。
- 音频元素不随筛选、toast、输入或保存状态重建；换任务时停止旧音频、清理监听和迟到请求。

### 4.2 管理端：稳定外壳、任务明确

保留六个业务入口：Overview、Annotators、Tasks & corpus、Quality、Cross-checks、Activity log。

| 页面 | 改造重点 |
| --- | --- |
| Overview | 当前存量与日期内活动分区；首屏只强调主要指标，其余以紧凑明细呈现；消除口径不清的重复卡片 |
| Annotators | 列表与个人详情分清；场景权限表单独立，切人时保留/提示未提交输入；迟到响应不覆盖下一人的内容 |
| Tasks & corpus | 共享筛选栏、匹配总量、表格和详情抽屉；总量必须与当前过滤条件一致 |
| Quality | 质量信号引导到具体队列，批量操作只在选中记录后出现；保留“信号不是自动结论”的必要解释 |
| Cross-checks | 队列与审阅独立；左右稿件、音频和差异说明对齐；窄屏用明确标记的上下布局；裁定区固定且不遮挡正文 |
| Activity log | 可检索表格和详情；沿用现有导出“可见记录”范围，不把按钮扩大解释为全量导出 |

日期筛选跟随它实际影响的内容：Overview 中的 stock 与活动指标要明确区分；Cross-checks 沿用现有默认全时段逻辑，不能无意继承 Last 30 days。筛选标签放在输入上方，用网格控制换行，避免交叉质检页把多个长标签挤成一排。

主侧栏只保留导航。标注员目录进入 Annotators 视图中的可搜索列表，避免所有管理页面都为目录保留固定宽度。

### 4.3 登录与个人记录

- 登录以用户名输入和继续操作为视觉中心；保留会话接管、过期原因提示与公共统计功能；速度图和排行榜作为次级信息，窄屏放在登录表单后面。
- 图表保留最近 28 个自然日、四段七日平均线、现有时区和场景筛选语义。不会为了换图表样式改变统计逻辑。
- 个人记录采用搜索/状态筛选 + 表格 + 详情；继续使用 `include_submissions=1` 的统一列表及 `version_id` 详情。
- 标注员看见普通完成/跳过记录；不恢复 `My cross-checks` 标签、复标徽章、质量状态或裁定提示。
- 纠正入口在存在未完成任务时保留现有限制并解释原因；草稿纠正与已发布版本关系保持不变。
- 旧 `tab=cross-checks&round=...` 链接继续转换成普通详情，兼容旧 sessionStorage 提示，展示内容仍为普通任务反馈。

### 4.4 响应式与双向文字

- ≥1280px：完整桌面布局；1440px、1920px 不出现无意义的大面积空栏或过度拉伸。
- 768–1279px：管理导航折叠，辅助信息转抽屉；筛选按预定网格换行，主要编辑功能完整可用。
- 390px：登录、历史、主要浏览与基本编辑操作可用；复杂表格允许容器内横向滚动，页面本身不溢出；不能直接隐藏已存在的功能。
- 额外检查 200% 浏览器缩放，关键按钮与错误信息必须可达。
- UI 保持 LTR；阿拉伯语正文明确 `dir="rtl"`，文件名/编号/时间使用独立方向隔离；不能用整页 RTL 修复单个输入框。
- 覆盖阿拉伯语与英文混排、数字、标点、组合字符、emoji；差异展示保留后端偏移语义，不能擅自 trim/NFC 后再标记。

## 5. 架构与不可回归的业务边界

建议目录：

```text
frontend/
  package.json
  package-lock.json
  vite.config.ts
  src/
    app/              # providers、入口、路由、错误边界
    theme/            # token、两种主题、静态样式配置
    components/       # 上述共享组合组件
    api/              # fetch 封装、类型、query keys、错误映射
    features/
      auth/
      workspace/
        editor/       # 分段、场景核验、输入状态
        media/        # 音频、Canvas、播放同步
        persistence/  # 保存队列、离线草稿、outbox
      history/
      admin/
        overview/
        annotators/
        corpus/
        quality/
        cross-checks/
        audit/
    dev/              # 仅开发环境的组件与边界数据样例
    test/
  dist/               # 构建产物，不提交源码仓库
```

### 5.1 状态分别由谁管理

1. **服务器数据**：Query 管理列表、统计、详情。query key 包含角色/用户、资源和全部筛选条件；切换身份清理相关缓存，登录状态不持久化进公共缓存。
2. **可编辑草稿**：工作台 store 管理原始值、dirty 和已确认快照。后台 refetch 不得替换当前输入；每行只订阅自己需要的状态。
3. **媒体状态**：audio ref、Canvas、必要的动画帧独立管理。播放时间更新不能让整个表格重渲染。
4. **会话与保存协议**：独立服务负责计时器、冻结写入、队列与 IndexedDB。React mount/unmount/StrictMode 重放不能产生第二个保存器或重复心跳。

Query 默认可能在重新聚焦、重连等时机重新取数。编辑器和写入链路需要显式策略，不能照搬列表默认设置。[TanStack Query 默认行为](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)

### 5.2 保存与离线迁移

- 同一 assignment 同时只有一个在途保存；发送前冻结 payload，确认后只清除该次快照已涵盖的修改。
- 保留 `lease_token`、`expected_revision`、`operation_id`；同一次请求重试使用原 ID 和原内容，不能每次生成新 ID。
- 文本、时间边界、质量标记、场景核验进入同一有序保存流程；场景核验单独修改也必须保存。
- 完成/跳过前处理尚未提交的最新输入，沿用原子终结协议；响应丢失时安全重放，不能靠按钮变灰推断成功。
- 401/会话被替换/停用立即冻结写入；409 保留本地稿件并展示冲突处理；429/暂时性失败采用有上限退避；不无限重试永久错误。
- 任务、用户或详情切换后，旧响应不能更新新上下文。请求取消只是辅助，仍要验证 task/lease/version/generation 等标识。
- 第一版保持 IndexedDB 名称、store、schema 和 draft/outbox 语义兼容；确有升级需求时使用版本化、可回退的迁移。旧版到新版、新版回旧版均要验证未同步草稿和未确认请求。
- 保留字体偏好、会话提示和 flash 等已存在的 localStorage/sessionStorage 兼容；不清空用户存储来解决迁移问题。
- `mode/round_id` 等内部信息可用于正确恢复，用户可见提示与复制出的草稿继续过滤，不泄漏盲标信息。
- IndexedDB 禁用/容量满要让用户知道本地持久化失败；不能宣称本地已保存。离线支持限于已有页面/草稿能力，首版不增加 Service Worker 或离线启动承诺。

### 5.3 管理权限、口径与内容安全

- 沿用独立 admin Cookie、Session、CSRF 和现有二次密钥要求；不引入前端 token 存储替代机制。
- 撤销/停用保留预览、影响范围、expected-version、幂等 ID 和确认；成功以服务器结果为准，不做乐观成功提示。
- 权限范围保存、抽样配置、质检裁定发生冲突时保留管理员输入，再明确展示最新服务端状态。
- 质检抽样 bps、Unicode diff 偏移、是否超过阈值、训练资格与 published 状态沿用后端契约；前端不另写一套业务判定。
- 来源证据、文件名、评论、转写和错误文本按文本渲染；来源链接继续限定安全协议，不用 HTML 拼接修复样式。
- 保留场景 metadata/review 的 feature flags、范围限制和空目录加载行为。

## 6. 构建、路由与部署接入

### 6.1 入口兼容

| 既有入口 | 接入策略 |
| --- | --- |
| `/`、`/index.html` | 同一工作台；保留服务端会话检查与 reason 跳转 |
| `/login.html` | 新登录页；已登录用户继续回当前工作入口 |
| `/completed.html` | 新个人记录；保留旧 query 转换和详情定位 |
| `/admin`、`/admin/`、`/admin/login` | 同一管理应用，保留会话初始化与 `view/range/from/to/annotator/round/...` 查询参数 |
| `/api/**` | 继续由原后端处理；未知 API 必须返回原错误，不可 fallback 成 HTML |
| `/api/audio/**`、`/api/admin/audio/**` | 保留鉴权、Range、X-Accel-Redirect 和各自角色访问边界 |

首版保留管理端 query 路由，避免为美化 URL 额外扩张后端 catch-all。管理端与标注端按路由拆包，登录页不加载裁定界面和整个编辑器。跨旧/新页面阶段，应用组之间使用完整导航，确保命中后端版本选择。

### 6.2 生产构建与静态文件

1. 在 `frontend/` 固定 Node、npm 和 lockfile；提供 `dev`、`typecheck`、`lint`、`test`、`build` 命令。
2. 构建在 CI/打包环境完成。发布包包含 Python 应用需要的文件和 `frontend/dist`，线上继续由 Gunicorn/Flask/Nginx 提供服务。
3. Flask 只为已知页面入口返回对应 HTML；新增受限的构建资源目录，例如 `/assets/`，避免放宽现有 `/static/` 白名单到仓库任意文件。
4. 本地集成测试由 Flask 提供同一产物；生产可让 Nginx 直接提供 hash 资源，限定到 dist/assets 目录。绝不把整个仓库或音频目录变为公开静态目录。
5. HTML 与会话响应继续不缓存；hash 资源使用长期 immutable 缓存。发布期间保留上一版本 hash 资源，覆盖旧标签页的延迟加载与回滚窗口。
6. 构建输出缺失要让发布预检失败，不能静默让一部分页面回旧版。记录源码提交与产物校验值，切换 release 目录时保持 HTML/资源一致。
7. 字体、图标、图表脚本均来自同源；使用系统字体或有许可的本地字体，不请求 CDN/Google Fonts。
8. Vite dev proxy 代理 API 并验证 Cookie；生产验收使用真实 Flask 响应头，不能只在 Vite 开发服务器上检查页面。

### 6.3 CSP 是选型的第一道实测门槛

Ant Design 默认的运行时样式与当前 `style-src 'self'` 存在需要解决的兼容问题。优先验证 `zeroRuntime` 与构建期静态样式提取；两种主题、变量、图标、Modal、Select、DatePicker、Tooltip、Table 固定列/滚动都要在真实 CSP 下打开、操作、截图。官方同时提供 CSP nonce 配置，但它不是所有样式问题自动解决的保证。[ConfigProvider 的 CSP 支持](https://ant.design/components/config-provider/)

若静态方案仍需受控样式注入，先验证服务端每响应生成 nonce、传递到组件样式系统与 CSP 的小范围适配；不得直接加入宽泛 `unsafe-inline` 来通过验收。如果在限定验证阶段仍无法同时满足严格 CSP 和稳定交互，就在大规模迁移前改选 shadcn/ui + 构建 CSS，并重新验证同一套样例。此时是替换主库，不是两套混用。

### 6.4 渐进切换与回滚

- 暂设服务端两个独立开关：管理端旧/新、标注端旧/新；标注端登录、工作台、历史作为一组验证。默认旧版，随阶段启用。
- 新旧页面共享同一套现有 API 与数据库规则；新增开关不能改变数据解释或权限。
- 对每个开关测试刷新、直接链接、登录跳转、混合导航与音频；完整切换前仍保留旧资源。
- 回滚通过切回页面入口/上一份产物完成，不回滚数据库；特别验证新版留下的 draft/outbox 能被旧版接续。
- 稳定运行并完成回滚演练后，单独删除旧 HTML/CSS/JS 和临时开关。实施阶段先从独立测试环境验证，正式发布另列发布步骤。

## 7. 分阶段任务与交付

以下为单人连续投入的粗估，共 **14–21 个工程日**，不含外部评审等待。P0/P1 后按真实组件兼容性与业务复杂度重估；不按页面数量承诺一天重写完成。

| 阶段 | 工作及交付物 | 完成标准 | 估算 |
| --- | --- | --- | --- |
| P0：基线与契约 | 重跑当前 UI；截图/问题清单；入口-功能-API-测试对应表；统计典型和最大分段；记录旧版浏览器存储结构 | 每项现有功能有迁移位置与验收；高风险流程没有遗漏 | 1–2 日 |
| P1：底座与代表页 | Vite/TS/依赖锁定；Flask 产物入口；CSP 样例；主题与共享布局；一个真实数据管理表格；一个含长阿拉伯语输入的工作台样例；保存服务最小技术验证 | 生产构建通过 CSP/音频/输入验证；两个代表页布局站得住；确定唯一组件库 | 2–3 日 |
| P2：管理端只读功能 | Overview、Annotators 只读、Corpus、Quality、Activity、Cross-check 队列/对照；共享筛选、详情、图表 | 查询参数、日期口径、总量、分页、角色鉴权一致；各种状态和截图验收通过 | 2–3 日 |
| P3：管理端写操作 | 场景权限、撤销/恢复、释放、停用、抽样设置、质检裁定/取消；复用确认流程 | 预览/CSRF/二次密钥/冲突/幂等/迟到响应回归通过 | 3–4 日 |
| P4：标注端迁移 | 登录、完成记录、工作台；按会话→IndexedDB→保存队列→音频→编辑→提交/历史顺序接入 | 任务恢复、离线重放、场景单独保存、盲标、阿拉伯语、快捷键全链路通过 | 4–6 日 |
| P5：收尾与切换准备 | 全量回归、视觉对比、性能检查、资源缓存/Range 验证、发布包和回滚演练；形成验收报告 | 无阻断问题；所有例外有证据与处理结论；可重复构建和回滚 | 2–3 日 |

建议按可审查增量提交：底座与 tokens → 共享组件及管理只读页 → 管理写操作 → 登录/历史 → 工作台保存与媒体 → 工作台编辑与终结 → 验收与切换。不要把整个前端重写塞入一份无法逐项检查的巨大 diff。P1 就验证编辑器高风险技术点，不拖到管理端完成后才发现选型不合适。

P1 的代表页面是视觉方案的检查点：用真实长度的数据看信息密度、对齐、字体和主次，再按同一套规范铺开；若调整风格，改 tokens 和公共组件，不在后续页面各自加补丁。

## 8. 验收：业务正确与视觉正确都要有证据

### 8.1 功能回归矩阵

| 场景 | 必须证明的结果 | 可复用的测试入口 |
| --- | --- | --- |

| 完成/跳过/释放 | 原子提交、正确反馈、重复点击与响应丢失无重复结果 | 工作台/API/assignment 与 cross-check 现有测试 |

| 管理写操作 | 预览、确认、CSRF、版本冲突、请求丢失/响应丢失均符合现有规则 | `tests/test_admin_api.py`、`test_cross_check_regressions.py` |
| 语言与 diff | 英文 UI、阿拉伯语输入、Unicode code point 高亮、旧链接兼容 | `test_english_platform_acceptance.py`、`test_cross_check_diff.py` |

表中省略前缀的文件位于 `tests/browser/`。实现时补充每项迁移测试的具体节点，不能用删除旧测试或统一 skip 换取通过。

现有浏览器测试大量使用 `#id`、原生 `select_option` 和旧页面结构。迁移时保留有业务意义的 ID，或同步改成角色/名称定位与明确的 test ID；断言仍验证原业务行为。改了 UI 结构不代表可以减弱竞态、鉴权或盲标断言。

### 8.2 视觉与可用性验收

固定浏览器、字体、时区和种子数据，对登录、工作台、记录、各管理视图及关键弹窗保存截图和差异图。

- 主要尺寸：1440×900、1366×768、1920×1080、1024×768、390×844；重点覆盖 1366×768 的工作台首屏效率。
- 关键状态：加载中、无数据、长文件名、长用户名、长阿拉伯语、多行错误、筛选多选、未授权、离线、冲突、只读、密钥校验错误。
- 正常桌面工作台首屏同时可见任务/保存状态、播放入口和至少一个可编辑分段，不能全被场景核验和统计占据。
- 同一工具栏控件等高、内容边界对齐；不靠负 margin、绝对定位或大量 `!important` 逐点修补。
- 页面级无横向溢出；必要横滚限于表格/波形；固定列和工具栏不覆盖内容与焦点。
- 长值不能把按钮推出屏幕；文本省略有完整查看途径；弹层在滚动和缩放后仍对准触发器。
- 鼠标与键盘均可完成常用流程，Tab 顺序合理，关闭弹窗恢复焦点；自动保存提示不能抢焦点。
- 普通文字对比度以 4.5:1 为目标；状态不能只靠色彩；阿拉伯语编辑字号不因“紧凑模式”被压缩。
- 截图对比增加布局边界断言与人工逐页检查；更新基线必须说明布局变化原因，不批量接受未知差异。

### 8.3 性能与可靠性预算

先测当前实现，再以同一浏览器、同一数据和同一网络条件比较。以下是拟定门槛，不是现有测量结果。

- 数据规模覆盖典型任务、当前观测最大任务，以及 100/500/1000 分段压力夹具；10 万语料仍由后端分页处理。
- 编辑输入目标为本地 key-to-paint p95 ≤50ms；输入不能带动整个表格、图表和波形重建；无输入丢失、光标跳动和 IME 截断。
- 波形拖动/播放保持响应；React 提交不随每一帧播放时间发生全页更新；开发 profiler 与浏览器 trace 提供证据。
- 连续切换 50 个任务后没有持续增长的 audio listener、interval、Canvas 或媒体实例；同一任务最多一个在途保存。
- 管理列表默认使用服务器分页；有 cursor 的 API 继续上一页/下一页或加载更多，不伪装支持任意页码/全库前端排序。
- 分段数实测导致卡顿才引入虚拟化。Ant Design Table 支持虚拟滚动，但还需验证变高文本、焦点、键盘跳行和滚出视口不丢稿；不够用时仅为该业务组件引入专用虚拟列表。[Table 文档](https://ant.design/components/table/)
- 首次进入管理页面与工作台分别记录压缩资源量、可交互时间、长任务与请求数。路线拆包；预算按 P0 数据在 P1 固定，不能仅用 Lighthouse 分数代替编辑性能。

### 8.4 CI 与发布验收

- 独立前端检查：锁定安装、类型检查、lint、必要单元测试与生产 build；产物可供集成任务复用。
- PostgreSQL 16/18 现有测试矩阵继续执行；浏览器启动前确保 dist 产物到位。迁移期间按开关覆盖旧/新版，切换后新版是默认完整验收对象。
- 新增有价值的测试集中在保存状态机、存储兼容、路由/CSP/构建资源集成和视觉布局，不为每个按钮或静态 CSS 写镜像单测。
- 用实际 Nginx/Flask 组合核查刷新、深链接、Cookie、CSP、MIME、缓存、音频 206/Range、静态资源 404 与旧标签页加载。
- 发布包验证无外部运行时依赖；控制台没有未处理 JS 错误、资源缺失或 CSP 违规。
- 验收报告给出构建提交、实际执行命令、测试结果、前后截图、性能数据、未解决事项与回滚证据；截图不使用真实标注员敏感数据。

## 9. 第一批实施的明确范围

下一批代码工作应完成 P0/P1：建立基线、最小构建接入、CSP 验证、主题与共享组件，并交付“管理列表 + 真实交互工作台”的代表页面。代表页面必须有长文本、空状态、错误状态、窄屏和阿拉伯语输入，避免只有静态理想数据的漂亮截图。

本次任务已创建分支并写下计划。组件库推荐、默认主题、桌面优先策略属于明确提出的方案；页面和业务行为尚未开始替换。后续实现以用户的新反馈修订这些选择，现有 API、数据与用户草稿则始终按上述兼容要求处理。
